# 工作流 · 双机交接规则（2026-11-26 改版 v3.6，已定死）

**生效日期**：2026-11-24　**改版**：2026-11-25（每个项目独立收发）／2026-11-26 v3.1（接手后自动清发件箱；接管顺序）／2026-11-26 v3.2（§1.2 改为"母版 + 项目副本"；§4.0 命令区分 mac/x86）／2026-11-26 v3.3（进度包文件名以项目名开头）／2026-11-26 v3.4（去掉本机项目名/路径硬编码，示例改占位名）／2026-11-26 v3.5（接手前加路径预检、越界整包拒收；发件箱改为默认保留，`--clean-outbox` 才清）／2026-11-26 v3.6（`装交接.py --scan` 报告按 `.no-handoff` 退出的目录；插件自测脚本加目录位置与安装器检查）
**目的**：在 macOS 与 x86 两机之间来回切换时，不靠记忆、不靠口头描述，只靠固定的包完成接力。

---

## 一句话规则

> **每个项目自己打包、自己接手；离开 → 先在项目里跑打包，接手 → 先在项目里跑接手。**
> 每台机器上"最新的工作进度"只有一个来源：那个项目目录里的实际文件；包只是快照。

---

## 1. 目录布局

### 1.1 每个项目 = 独立工作区根

所有项目一律自带一套，**不再有"嵌套子项目"这种类型**：

```
<项目>/
├── bin/打包进度.py      ← ROOT 由脚本位置推导 = 这个项目
├── bin/接手进度.py
├── 收件箱/              ← 对方传来的本项目进度包
├── 发件箱/              ← 本机打好、等待传出的包
└── …项目自己的内容…
```

| 项目 | 位置 | 打包命令（在该项目根目录跑） |
|---|---|---|
| `项目A/` | 桌面 | `python bin/打包进度.py --lite` |
| `项目B/` | 桌面 | 同上 |
| 任意多个同级目录（各自的 `bin/` 自带脚本） | 桌面独立目录 | 同上 |

判据一句话：**只要这个目录里有 `bin/打包进度.py`，它就是自己的工作区根。**

### 1.2 公共层（`公共层/`，2026-11-25 前叫 `交接工作区`）

`公共层/` 本身**不是打包单位**，只提供这些东西：

- `tools/`：本机平台件（各机自备的包装脚本：解释器、渲染器、ffmpeg 等），唯一一份，永不进包；
- `bin/模板/`：标准脚本 `打包进度.py` / `接手进度.py` 的**唯一母版**，新项目从它拷；
- `工作流-双机交接规则.md`：本文件的**母版**（唯一权威版本）。**各项目根同时放一份同内容副本** —— 它随进度包一起传输，方便对端拿到；接手/合并补丁之后必须按 §4.0 用母版归一化，否则两份会漂移；
- `本机项目清单.md`：本机事实（解释器 / 平台件路径、项目入口、命令对照）；
- 其余：`plugins/`（插件源码快照）、`素材库/`（可复用素材）、`工具/`（单机小脚本）、`_日志/`（自动动作审计）、`_历史/`（归档）。

它的 `bin/` 只有 `打包引导包.py`、`装交接.py` 与 `模板/`，**不产出也不接手任何进度包**。
它只有一个 `引导包/` 目录：产出与收到的引导包都放这里，**不放进度包**。

### 1.3 新项目：交接是自动铺的

- 在桌面上新建一个目录后，**第一次在里面开会话**时，插件 `dsh-autohandoff` 就会把它铺成工作区根：
  `bin/打包进度.py`、`bin/接手进度.py`、`收件箱/`、`发件箱/`，并在 `AGENTS.md` 里补「交接」+「共用工具」两节
  （没有 `AGENTS.md` 就新建骨架）。每次动作写进 `公共层/_日志/自动交接.log`。
- 只认**桌面的一级子目录**（与 `公共层/` 同级）；`公共层/` 和插件配置里的 `exclude`
  一律跳过；已有 `bin/打包进度.py` 的目录不再动（幂等）。
- **不想被铺的目录**：在它里面放一个空的 `.no-handoff` 文件（临时草稿、素材中转站之类）。删掉文件就恢复自动铺。
- 插件没装、或刚装还没重启 DSH 时，手动等价：
  `python bin/装交接.py --scan` 看谁缺 → `--scan --apply` 一次补齐；单个项目
  `python bin/装交接.py ../新项目 --append-agents --init-agents`。
- **判据不变**：目录里有 `bin/打包进度.py` 才算工作区根 —— 自动铺就是保证这一条永远成立。

## 2. 两类包，两种命名

| 包 | 命名 | 内容 | 放哪 |
|---|---|---|---|
| 进度包 | `<项目名>-进度-YYYYMMDD-HHMM-<来源机>.zip` | 一个项目的全部内容 + `MANIFEST.json` + `00-包入口.md` | 项目的 `发件箱/` → 对端项目的 `收件箱/` |
| 引导包 | `引导-YYYYMMDD-规则与脚本.zip` | 规则 + 标准脚本 + `装交接.py` | 公共层 `引导包/` → 对端公共层 `引导包/` |

进度包的 `MANIFEST.json` 里多一个 **`scope`** 字段，值是项目目录名。接手方据此拒绝"合错项目"。

> **文件名以项目名开头（2026-11-26 起）**：批量传多个项目时，只有时间戳分不清是谁的包。
> 例：`项目A-进度-20261126-1254-mac.zip` —— 项目名打头 + 日期时间，末尾 `<来源机>` 标明哪台机器打的。

包内结构固定：

```
<项目名>-进度-YYYYMMDD-HHMM-<来源机>/
├── 00-包入口.md        ← 自动生成：范围（scope）、清单摘要、接手三步
├── MANIFEST.json       ← 每个文件的 sha256 / 大小 + scope
└── <项目原样>           ← 除忽略清单外的全部目录与文件
```

## 3. 离开一台机器之前（必做）

在**要离开的那个项目**里：

```bash
python bin/打包进度.py --list            # 先看会打哪些、多大（不写文件）
python bin/打包进度.py --lite            # 跳过 **/runs/ 与 generate/3d
```

脚本会自动：按忽略清单剔除平台件与缓存（§6）→ 逐文件算 sha256 → 生成 `00-包入口.md`（写明 `scope`）
→ 用 Python `zipfile` 打包（**带 UTF-8 名称标记**，Windows/x86 解压不乱码）→ 产出到该项目 `发件箱/`。

## 4. 接手一台机器之后（必做）

### 4.0 顺序：**先补丁 → 再接手 → 最后归一化**

刚拿到一批包（可能同时有公共层补丁包 + 若干项目进度包）时，按这个顺序，不要跳步：

```
① 公共层：合并补丁/引导包（装交接.py、bin/模板/两个脚本、规则文件）
② 公共层验证：装交接.py --scan（应"所有一级目录都已有交接脚本"）
              接手进度.py --help（应看到 --clean-outbox）
③ 逐项目：包放进 该项目/收件箱/ → 接手进度.py <包> --dry-run → 真接手
          （发件箱默认保留；确认要清旧包再加 --clean-outbox）
④ 【必做，最容易漏】逐项目归一化（显式传项目名；--scan --apply 对已有脚本的项目无效）：
          刷脚本：  mac：python3 公共层/bin/装交接.py <项目>
                    x86：python  公共层\bin\装交接.py ..\<项目>
          同步规则（装交接.py 不写规则文件）：
                    mac：cp      公共层/工作流-双机交接规则.md <项目>/
                    x86：copy /Y 公共层\工作流-双机交接规则.md <项目>\
⑤ 复核：各项目 bin/ 两个脚本同 sha256、规则文件同 sha256、--scan 全绿
```

**为什么不能只做 ③**：

1. **进度包会覆盖项目里的 `bin/` 与规则文件** —— 忽略清单只剔 `收件箱/` `发件箱/` `.dsh/` 与缓存，
   `bin/打包进度.py`、`bin/接手进度.py`、`AGENTS.md`、`工作流-双机交接规则.md` 都在包内。
   对方用旧脚本打的包，会把本项目刚更新的脚本冲回旧版。
2. **`--scan --apply` 补不了这个** —— 它的判据是"没有 `bin/打包进度.py` 才算缺"，已有脚本的项目直接被跳过。
   要归一化必须**显式传项目名**：`装交接.py <项目>`。
3. **`装交接.py` 不写规则文件** —— 只写 `bin/` + `收件箱/README.md` + `发件箱/README.md` + AGENTS 两节。
   规则那份必须自己拷（mac 用 `cp`，x86 用 `copy /Y`）。

反序也不至于坏（补丁合并是幂等的）：先接了项目包再合并补丁，只需补跑 ④。

### 4.1 怎么接

在**对应的那个项目**里：

```bash
python bin/接手进度.py 收件箱/<项目名>-进度-YYYYMMDD-HHMM-<来源机>.zip --dry-run   # 先只校验
python bin/接手进度.py 收件箱/<项目名>-进度-YYYYMMDD-HHMM-<来源机>.zip
```

脚本按顺序过四道，**任何一道不过都不落盘**：

1. **scope 校验** —— 包的 `scope` 与当前项目目录名不一致 → 拒绝（`--force` 可强解）；
2. **签名查重** —— `收件箱/.已接手.json` 里已有这个包的记录（字节相同）→ 拒绝（`--force` 可强解）；
3. **逐文件 sha256** —— 与 `MANIFEST.json` 不符 → 中止；
4. **路径预检** —— 先把全部目标路径算出来；任何一条越界/非法（反斜杠、`..`、盘符、指向根外的链接）
   → **整包拒收**：一个文件都不写、不记签名、不清发件箱。`--force` 不豁免这一条；
5. 合并解压（跳过包元数据），在 `收件箱/接手记录-YYYYMMDD-HHMM.md` 写下：包名、scope、覆盖了哪些文件。

**发件箱默认不动（v3.5 起）**：`发件箱/` 里的 zip 可能是"打好但还没送出去"的包，
接手成功不代表它们已送达，自动删会丢快照。要清就显式加 `--clean-outbox`（只清第一层 zip，
不碰 README、不递归子目录、不动 `收件箱/`）；清掉的包名写进当次接手记录的「收尾」小节。

解压完先读项目自己的 `AGENTS.md` / `README.md`，再干活。

> `.已接手.json` **不要删** —— 删了同一个包就能再合一遍，把文件覆盖回旧版。

## 5. 冲突与优先级

1. **包内文件覆盖本机同名文件**（包是快照，代表"对方那边的最新"）。
2. **本机独有、包里没有的文件不动** —— 两机并行改同一文件时以最后一次打包为准，这只能由人保证：**离开前一定要打包**。
3. 接手完就把包移走（删掉或移进 `_已接手/`）：收件箱里只放"待接手"，误合就无从发生。
4. 历史包与接手记录可以随时删，不影响项目本身。

## 6. 忽略清单（打包时自动剔除）

| 剔除项 | 原因 |
|---|---|
| `.local/` | 平台相关件：预编译二进制（体积可达 GB 级） |
| `收件箱/` `发件箱/` | 避免包套包 |
| `.dsh/` | 工具运行缓存（临时目录也在这里） |
| `node_modules/` `.git/` `.venv/` `venv/` `__pycache__/` `.idea/` `.vscode/` `.pytest_cache/` | 依赖与缓存，可重建 |
| `*.zip *.tar.gz *.7z *.dmg` | 已归档的旧包（注意：项目里的 zip 备份因此不进包） |
| `*.pyc` `.DS_Store` `Thumbs.db` | 系统与字节码垃圾 |
| `--lite` 额外跳过：`generate/3d/`、`**/runs/` | 体积大的生成结果与运行记录；可留本机 |

> **`tools/` 不再被剔除**（2026-11-25 改）：平台件已统一到 `公共层\tools\`，它不在任何项目里、本来就不会进包；
> 而项目自己的 `tools\` 是项目资产 —— 例如 `某项目\tools\build-data.cjs` 必须跟着包走。
> 如果哪个项目确实放了平台二进制，放进 `.local/` 或用 `--exclude`。

> 需要临时多加排除：`python bin/打包进度.py --exclude 某目录`（相对项目根，可重复）

> **读不了的目录会被"静默跳过"**：打包与 `装交接.py` 都走 `os.walk`，遇到权限拒绝的目录不报错、不中断，只是不收进去
> （实测：`某项目\_archive\…\pip-build-*` 这类锁死的临时目录）。所以"包打成功"不等于"项目里每个文件都进了包"，
> 目录里有锁死/异常权限的东西时，先自己 `--list` 对一下文件数。

## 7. 为什么这样定（踩过的教训）

1. **平台二进制绝不能跟着包走。** 曾经把 arm64 的 ffmpeg 之类打进包，x86 上直接 `cannot execute binary file`，
   而文档里所有命令都硬编码那个路径 —— 接手方卡在第一步还不知道原因。
2. **中文文件名必须打 UTF-8 标记。** macOS 自带 `zip` 打的包不带 EFS 标记，Windows 解压成乱码。统一用 Python `zipfile`。
3. **没校验就等于没交接。** 大包跨机传输容易截断，`MANIFEST.json` 逐文件 sha256 是唯一能确认"对方拿到的是完整的"的手段。
4. **同一个包能被合两遍（2026-11-25 修）。** 旧脚本没有签名文件，而 `收件箱/README.md` 却写着"有签名防重复合并" ——
   文档与代码不一致本身就是诱因。现在 `.已接手.json` 是硬门禁。
5. **跨项目的包会被合并到错误目录（2026-11-25 修）。** 旧脚本完全不看 `MANIFEST.scope`，
   把 A 项目的包丢进 B 项目会在 B 里凭空造一个 `A/` 子树。现在 scope 不符直接拒。
6. **Windows 控制台编码会让接手脚本"崩在校验之后"。** cp936 控制台遇到 `✓`/`✗` 会抛 `UnicodeEncodeError`，
   表现为"校验完就报错退出、文件一个没写"，极易误判成包坏了。脚本已改成 `[OK]`/`[X]` 并给输出流加 `errors="replace"`。

## 8. 两机环境差异（接手方只需记这两条）

| &nbsp; | macOS | x86 |
|---|---|---|
| 专用程序（渲染/仿真等示例） | `/Applications/<App>.app` | 环境变量指向的那份（例如 `DSH_<TOOL>_BIN`） |
| 视频工具 | 项目自带或 `tools/bin` | 自备对应架构版本（`tools\bin`） |

两者都**不在包内**，各自机器上装好一次即可。其余（Python 脚本、应用脚本、数据、文档）跨平台通用。

> **同一平台件在两机上必须同大版本。** 自动化脚本按 `--version` 探测时，版本号解析失败会静默跳过候选，
> 表现成"明明装了却找不到"；排查时先看版本输出格式有没有变。**不要再往 `tools/` 里放第二份**，否则又是一次版本分叉。
